## 0. 通用改造规则（每个文件都适用）

1. **平铺导入**：模板里所有 `from knowledge.xxx import ...` 一律去掉 `knowledge.` 前缀
   （如 `from core.paths import ...`、`from processor.import_process.base import BaseNode`）。
2. **入口变化**：应用装配在根 `main.py`；模块里不要自带 `uvicorn.run` 主入口（可留 `if __name__` 调试块）。
3. **配置来源**：一律走 `.env`（`processor/**/config.py` 的 `from_env`），不要硬编码 IP/密钥。
4. **异常**：必须继承 `processor/import_process/exceptions.py` 或 `query_process/exceptions.py`
   中已定义的异常族，禁止裸抛无上下文异常。
5. **进度与耗时**：节点执行前后要埋点（`utils/task_util.py` 的 add_running/add_done/add_node_duration），
   这样 `/status` 与前端进度才能工作。
6. **命名对齐**：方法/类名尽量与模板一致（便于对照评审与后续 diff）；
   `ducment_split.py` 的拼写按模板保留。
7. 业务语义暂不替换：`item_name` 等字段名先保留模板叫法（V1 元数据平铺方案见需求评审 7 节）。

## 3. 导入链路（核心，路线 2–6）

按模板 git 顺序实现，每完成 1–2 个节点即可叫我评审：

1. `processor/import_process/config.py` → `ImportConfig.from_env`
2. `state.py`（已实现）→ `nodes/entry.py`
3. `nodes/pdf_to_md.py`（MinerU；先确认 MinerU 服务可访问或按 .env 走本地/云端）
4. `nodes/md_img.py`（图片处理三件套：扫描→VLM 摘要→MinIO 替换）
5. `nodes/ducment_split.py`（标题分块/长拆分/短合并；分块时把“章节标题层级”带进 chunk 元数据——V1 章节来源）
6. `nodes/bge_embedding.py` → `nodes/import_milvus.py`（建集前确定标量列）
7. `nodes/item_name_recognition.py` → V1 从简：先保留“文件级对象名识别”，字段不做复杂化
8. `main_graph.py` 把节点串成图 → 用单测/小脚本跑一个 PDF 冒烟

**导入链路验收**：上传 1 个 PDF → `/status` 显示节点流转 → Milvus 集合有数据 → `/import` 页不崩。

## 我评审时会重点看什么

1. 与模板实现相比漏了哪些私有方法/边界处理（分块的长短阈值、图片替换的正则、重试与限速等）；
2. 平铺改造是否彻底（残留 `knowledge.` 导入会直接报错）；
3. 异常是否归属正确异常族、是否会让任务容器进入“失败”而不是让服务崩；
4. 每个节点是否做了进度/耗时埋点（否则 `/status` 是空的）；
5. 配置是否仍从 `.env` 读取、有无硬编码；
6. 是否符合“一切从简”决策（没偷偷引入新结构/新依赖）。
